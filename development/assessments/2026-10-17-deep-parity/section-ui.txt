Attitude: what is actually the same, and what differs

Both apps call the radio's lcd.drawHudRectangle. Toolbox X.HR is a direct alias, and both its AHR main panel and ATT secondary panel use that primitive. AERODECK's rectangular PFD is not a hand-written replacement for the native sky/ground algorithm. Native EdgeTX2.12.4 source cached at work/edgetx/api_colorlcd2124.cpp:1307 shows the same pitch projection used by the AERODECK overlay: dx=sin(roll)*pitch, dy=cos(roll)*pitch*1.85, pivot at the viewport midpoint, horizon angle=-roll. The current PFD's fixed datum is (240,154), native field x78..402/y64..244. Equal side tapes leave the central horizon region x124..356. Clipped overlaid rungs use the same projection. Drawing primitive versus mask alone is neither functional superiority nor a performance result.

Toolbox TBS GYRO converts CRSF radians to degrees, negates pitch only, and leaves roll/yaw signs. AERODECK does the same for radians, using metadata-qualified sensor values and current flags. Degree-valued inputs are already treated as normalized. That last convention still needs separate validation on non-CRSF sources. Both transmit latest values directly; no temporal smoothing/interpolation is proven in the inspected rendering/conversion paths. AERODECK adds signed20-degree pitch captions,10-degree rungs, large fixed aircraft wings with halo, larger heading badge and P/R readouts. The original AHR has speed/altitude scales, native horizon, aircraft bitmap and P/R numbers but no moving pitch-ladder loop or ladder image. Toolbox's ATT ring is a cached fixed graduated angular perimeter, not a moving pitch ladder; its moving green dot uses yaw. AERODECK lacks the graduated angular reference, and numeric bank alone is not proven equivalent for glance recognition. A substitute need not copy the circular bezel. AERODECK currently exposes yaw only as a raw Telemetry value, while its Flight compass is GPS course Hdg. Course over ground must never be described as yaw/magnetic heading.

Original AHR prioritizes airspeed when present and can show ground speed as auxiliary. It prioritizes GPS altitude with barometric altitude fallback/auxiliary. AERODECK samples ASpd but its Flight tape is always GS; GAlt/Alt feed a single undifferentiated ALT value. These are real conditional instrument capabilities to implement, not decorative differences. AHR can also project relative home direction into the horizon and CMP can compare home/course direction simultaneously. AERODECK gives home distance in Flight and bearing on another GPS page; it lacks an in-Flight direction-to-home cue.

AERODECK correctly refuses to render a fabricated level field when either pitch or roll is unavailable. Original AHR/ATT native calls use zero fallbacks and then dashboard currentness/dim treatments. That is a useful AERODECK distinction, but target hardware currentness still needs verification. AERODECK polls attitude before its draw throttle (and again when drawing), while rendering defaults25fps, bounded by ceil(100/renderHz) hundredths. Toolbox ML.run services its MSP/background path, updates attitude/baro/airspeed/GPS, then UI tasks. No simple equality of draw primitives or draw FPS proves equality of received samples, lifecycle or sustained latency.

The user's reported launch-fast/then-slow behavior is not resolved by a clean still image or a20fps draw count. Current release explicitly records hardwarePerformanceMeasured=false. To close this requirement: same TX16S/firmware/model/quad, same250Hz and1:64STD settings, Toolbox versus current exact AERODECK hash, ten-minute sustained tilt stream. Record incoming value-change times, draw cadence, p95 input-to-display latency, longest stall, current/peak heap and growth after launch2s/1min/10min. No SD logging in every render callback. Desktop3.0 WASM is not a benchmark for target2.12.4.

Flight and common status gaps

Core LQ/RSSI/SNR/Tx power and aircraft pack voltage/current/used capacity/percent/derived average cell voltage are present. Power now explains OFF, NOT FOUND, STALE and INVALID separately, supports genuine numeric0, source refresh and five pack favourites with remaining capacity. Those features are backed by current exact-source native synthetic screenshots, not guessed from mockups.

AERODECK does not replace the actual selected model timer: Toolbox TMR reads model.getTimer, while AERODECK flightSeconds is an app-session counter from a mapped radio arm indicator, updated only while full app runs and displayed on ArmInfo. Likewise, transmitter battery state, distinct Airmode/RTH/Turtle indicators, actual throttle percentage/limit and individual cell-array presentation are absent or only partly represented. A native CRSF per-cell feed from the connected Betaflight/ELRS quad has not been proven: this is a conditional renderer/backend requirement, not a claim that the quad supplies those cells. Never fabricate individual cells from pack average. These functions remain in scope. Toolbox FCD also exposes FC target/manufacturer identity and hardware sensor ACTIVE/UNAVAILABLE/UNHEALTHY states. Current Diagnostics version/API does not cover all identity fields, and EdgeTX discovered telemetry sources are not a substitute for FC sensor health. The decorative model bitmap can be optional, but active model identification must be unambiguous;54px fitted model text may need a full-name detail.

Toolbox's non-dashboard shell keeps RC/model battery sidebars around all modules. AERODECK devotes that space to content; normal footer instead carries mode, local-home distance, satellites and arming summary. Alerts remain global, but continuous pack/link values are absent from GPS/Setup/Tools/Video. Whether threshold-only monitoring is equivalent must be evaluated as a task, not dismissed because those values exist on Data/Flight. Do not require identical sidebars; require safe continuous health visibility with less clutter.

Video is not yet a VTX application. The current page truthfully says LOCAL NOTES / NO VTX COMMANDS and offers8 saved frequencies with derived known-band code, custom fallback and mini attitude. Toolbox dashboard VTX displays actual type/source/channel/frequency/power/PIT/LPD. VFV's long-ENTER invokes SN_VTX(send,frequency,band,channel), subject to actual supported transport/state. Real VTX status, protocol-aware read/apply/ack and favourite application remain missing; a prettier card cannot substitute. Key gating does not remove these requirements.

GPS: backend truth matters

Current GPS Details has valid current coordinates,7-decimal display, ground speed, course, altitude and explicit local home. Track/Home adds a bounded north-up metric trail, distance rings, zoom and off-plot handling. These are useful functions and distinct from Toolbox's small clamped relative-position inset. Both use Earth radius6371000 for distance calculations. Neither inspected helper alone proves persistent recovery after app/radio restart; do not claim such persistence without tracing actual log writers/readers.

AERODECK currently has no actual fix state, HDOP or per-satellite constellation/ID/quality-status/used/signal list; an independently supplied satellite-health field in Toolbox remains unproved. It truthfully says FIX TYPE NOT REPORTED. Its automatic home captures only while a GPS page renders and uses valid coordinates plus a satellite-count threshold; it is not FC Rescue home. Opening GPS later can capture a different location than takeoff. The local track also samples only while GPS pages draw and has no timestamps. Move shared home/history capture out of render paths, decide arm/fix semantics, and label app-local versus FC-reported reference clearly. Estimated time home is absent; Toolbox POS displays ETH from distance/speed. Toolbox GPS helper also has a Plus Code encoder, but no user-facing caller was found in inspected UI, so that row explicitly distinguishes code capability from proven exposure.

Critical warning against cargo-cult parity: original TBS/CRSF GPS bytecode sets POS_FIX to Sats > configured GPS_SATS2FIX. It sets GPS_HDOP to POS_FIX and clamp(Sats−4,0,9), not measured HDOP. This is confirmed in original disassembly, not merely a decompiler artifact. Other backends may provide true fix/quality. AERODECK should implement supported genuine fields or explicitly label an estimate/unknown; copying the Toolbox “3D FIX”/“HDOP” labels over a count heuristic would recreate misleading semantics. Satellite detail display is a source-proven UI capability, but the transport/backend dependency must be verified before promising that the connected Betaflight/ELRS quad can supply it.

Navigation and all-screen inventory

Current12 destinations: Flight, Telemetry, Power, RC Link, GPS Details, Track/Home, Video favourites, Configuration, Stick Guide, Sensors, Diagnostics, Arm Info. They are grouped into6 stable sections. Top icons are30px; context/footer glyphs18px. Flight itself hides the Instruments/Arm Info local tabs and uses the compass band; Arm Info exposes those two tabs. The global footer remains on both. Touch primary targets, SYS-focus caption/rotary/ENTER, PAGE section cycling, local context controls and RTN parents form the current contract. Navigation need not copy Toolbox's dashboard multiplexing/quick menu. Every underlying function still needs a sensible destination. The icon-only primary bar is aided by active plate/underline and SYS selection caption; recognition still needs first-user testing because not every icon is universal.

The global arming shortcut and origin return are useful:48×26px persistent footer target; returns from GPS or Setup to original context and draft. Warning overlay keeps that target. Alert focus is cleared when a warning disappears, before Setup draws; portable/native regression evidence is separate from this read-only audit. ArmInfo differentiates unknown flags, stale status and decode errors. No target is proof of armed state.

Telemetry's measured fitting is implemented. An earlier candidate that discarding fittedText's returned font caused a table overflow was checked and withdrawn: fittedText called with SMLSIZE remains SMLSIZE and truncates. Sensors has fixed character truncation and fixed columns; RC detail has direct large values. Those remain unmeasured extreme-value fit risks, not claimed observed overlap. Native stress should cover every page's long model/FM/source names, wide glyphs, missing data, large/negative values and all warning/footer combinations.

Only20 small icon masks are opened by current main. Packaged39 runtime files include33PNGs:7 at30×30 and13 at18×18 current icon masks, plus13 retained legacy full-panel/status PNGs. Legacy files do not imply current bitmap draw cost. Editable MaterialOutlined source/master SVGs, export mapping, official URLs and Apache notices exist under development/icons/material. Exact hashes/dimensions are saved in ui-evidence. Both apps cache masks. Both also allocate some local closures/tables in draw paths; neither is allocation-free. Benchmark memory/stalls rather than awarding superiority for vector drawing.

Four theme families (CARBON_PLATE,LEATHER_BLUE,METAL_SILVER,WOOD_WALNUT) have96 RGBA overlayPNGs:32 per resolution,8 screens per theme. Palette loading and optional overlays are functional adaptation machinery; exact decorative textures are optional. AERODECK currently has hard-coded480×272 fullscreen geometry and3 accent colors, not alternate resolution layouts or selectable full contrast themes. Compact widget does use zone sizes and is an AERODECK addition: the original Toolbox loader displays Select APP mode layout instead of compact telemetry in a non-fullscreen zone. Toolbox background behavior is not established merely by ML.bg existing: original loader tests APP.initDone, whereas M returns{G,F,D,X} and sets G.initDone. Fullscreen480×320/800×480 adaptation and broader input/capability matrix remain required under the clarified scope. A fallback string320X240 is not proof of a packaged supported layout. OT in Toolbox means one-time tool, not evidence of OpenTX support; do not infer firmware compatibility from that acronym.

Current native evidence is EdgeTX3.0 WASM480×272 with synthetic AOS5 telemetry and preferences,22 POWER-LIVE frames matching the exact main/widget/decoder/transport hashes. It does not verify actual2.12.4 font/color/runtime limits, hardware pose, sustained telemetry cadence, widget execution or30–40cm outdoor readability. Prior other-page/pose screenshots are useful historical evidence only if their differing source hashes are stated. No fixture-prefix code or test settings may ship.

Recommended acceptance order

1. Preserve current design and fix real data trust/lifecycle first: stable sustained attitude, model timer semantics, home capture independent of page, correct provenance/freshness and distinct radio/FC states.
2. Add missing functional displays/actions: live VTX/PIT/power and confirmed favourite apply; actual timer/radio battery/throttle/indicators; airspeed/barometric source adaptation; individual cell arrays; real supported fix/quality/satellite details and ETH.
3. Verify each task on actual TX16S2.12.4 with physical inputs and the real quad. Test zero/missing/stale/late source recovery, arming transitions and source reconnects, not only synthetic “happy path”.
4. Extend480×320/800×480 and readable contrast themes using independent layouts; verify complete functions on each target. Avoid copying carbon skin or treating image assets as inherent performance.
5. Demonstrate better outcomes: fewer actions for frequent tasks, faster unambiguous recognition at30–40cm, measured stable latency/memory and clearer cause/recovery when data disappears. Claims must bind exact source, target and conditions.

No production files, radio files, SD settings or canonical source were modified by this audit.
